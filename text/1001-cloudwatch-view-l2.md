# CloudWatch View L2 Construct

* **Original Author(s):** @Serenata27
* **Tracking Issue:** #1001
* **API Bar Raiser:** @TBD

Add a `View` L2 construct to `aws-cdk-lib/aws-cloudwatch` for `AWS::CloudWatch::View`. Today only the L1 `CfnView`
exists: an invalid view name is caught only when the deployment starts, and a view cannot be imported by ARN or passed
around as a typed construct.

### README

*The README text below becomes the `## Views` section of the `aws-cloudwatch` module README.*

#### Views

A view is a named SQL query over your CloudWatch telemetry. It stores the query, not the data: each time you query the
view, its definition runs against the underlying data.

```ts
const view = new cloudwatch.View(this, 'AppErrors', {
  definition: "SELECT `@timestamp`, `@message` FROM \"logs.default\" WHERE `@logGroupName` = '/my/app'",
});
```

This creates a view with a name generated by CloudFormation, based on the stack name and the construct's logical ID.
Use `view.viewName` to reference the view, for example in another query.

#### Creating a view

```ts
const view = new cloudwatch.View(this, 'AppErrors', {
  viewName: 'view.app_errors',
  definition: "SELECT `@timestamp`, `@message` FROM \"logs.default\" WHERE `@logGroupName` = '/my/app'",
  description: 'Error lines from /my/app',
  tags: { team: 'payments' },
});
```

`definition` is the SQL query that defines the view. See the
[SQL query reference](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/omni-sql-query-reference.html)
for the syntax. The service checks the definition when the view is created or updated, so an invalid query fails at
deployment time rather than at synthesis time.

Set `viewName` to choose the name of the view. Changing `viewName` replaces the view.

`tags` are applied to the view. Tags added with `Tags.of()` are applied as well.

#### Validation

When the values are not tokens, `View` checks them at synthesis time and throws an error if:

* `viewName` does not start with `view.` followed by a lowercase letter or digit, contains characters other than
  lowercase letters, digits, underscores and hyphens, or is not 6 to 256 characters long;
* `definition` is empty or longer than 10000 characters;
* `description` is longer than 1024 characters.

```ts
new cloudwatch.View(this, 'AppErrors', {
  viewName: 'AppErrors', // error: must start with `view.` and use lowercase letters
  definition: "SELECT `@timestamp`, `@message` FROM \"logs.default\"",
});
```

#### Querying a view

Reference a view by name in the `FROM` clause of a query. Quote the name with double quotes or backticks, because it
contains a dot. Select explicit columns and bound `@timestamp` on both sides, because the service currently rejects
queries with an open-ended time range:

```sql
SELECT `@timestamp`, `@message`
FROM "view.app_errors"
WHERE `@timestamp` BETWEEN NOW() - INTERVAL '1' DAY AND NOW()
```

`SELECT *` is not supported when querying a view.

#### Importing an existing view

To reference a view created elsewhere, import it by ARN:

```ts
const view = cloudwatch.View.fromViewArn(this, 'SharedView',
  'arn:aws:cloudwatch:us-east-1:123456789012:view/view.orders/0f1e2d3c-4b5a-6978-8796-a5b4c3d2e1f0');
```

A view ARN has the form `arn:<partition>:cloudwatch:<region>:<account>:view/<name>/<id>`, where `<id>` is generated by
CloudWatch when the view is created. `view.viewName` is derived from the ARN, and the imported view's account and
Region are taken from it. Views cannot be imported by name alone, because the `<id>` cannot be derived from the name.

## Public FAQ

### What are we launching today?

A new `View` L2 construct in the existing `aws-cdk-lib/aws-cloudwatch` module, wrapping the `AWS::CloudWatch::View`
CloudFormation resource.

### What is a view?

A view is a named, reusable SQL query that can be referenced from CloudWatch telemetry queries. It stores the query, not
the data. Views created through CloudFormation are user views; managed views are provisioned by AWS and are not
created by this construct.

### Why should I use this feature?

Use `View` to define views next to the rest of your infrastructure, catch invalid names at `cdk synth` instead of when
the deployment starts, and reference views created in other stacks by ARN.

## Internal FAQ

### Why are we doing this?

CloudWatch launched views (`AWS::CloudWatch::View`). Today CDK users must use the L1 `CfnView`, which accepts any
string as a name: an invalid name passes `cdk synth` and is only rejected by CloudFormation's pre-deployment
validation, before any resource is created. The `View` L2 validates the name at synthesis time, adds `View.fromViewArn()` and an `IView`
type that other constructs can accept, and gives views the same idiomatic API as the other constructs in
`aws-cloudwatch`.

### Why should we _not_ do this?

`CfnView` already exposes every property, so the L2 is a thin layer. We keep the surface minimal (four props, one import
method) so it is cheap to review and maintain. Grants are deferred to keep v1 minimal: `ViewGrants.read` is additive
and can be added later without a breaking change, preferably after the Service Authorization Reference documents the
full `view` ARN (a correction is in progress). Query access cannot be scoped to a view at all.

### What is the technical solution (design) of this feature?

* `View extends Resource implements IView`, with a `CfnView` default child. Props map one to one:
  `viewName → Name`, `definition → Definition`, `description → Description`, `tags → Tags`.
* `IView extends IResource, IViewRef` exposes `viewArn` (`Fn::GetAtt Arn`) and `viewName` (`Ref`). `IViewRef` is
  generated from the CloudFormation spec, and `CfnView` implements it too.
* There is no `ViewBase`: with a single import method, the local import class implements `IView` directly.
* `fromViewArn` derives the view name with `Arn.split` for a literal ARN, and with `Fn::Select`/`Fn::Split` for a token.
  It parses the ARN itself rather than reusing `CfnView.fromViewArn`/`CfnView.fromViewName`: the generated `arnTemplate`
  for `AWS::CloudWatch::View` is `...:view/${ViewName}`, without the id, because the Service Authorization Reference
  currently omits it, so `CfnView.fromViewArn` would return `<name>/<id>` as the name and `CfnView.fromViewName` would
  build an ARN without the id. A correction to the authorization reference is in progress.
* A view stores only its SQL text, and deleting it does not delete any telemetry, so `View` is `@stateless` and has no
  `removalPolicy` prop.
* A prototype exists: the construct, 21 unit tests, a README section and two integration tests (`integ.view-default`
  with only `definition`, `integ.view-all-props` with every property, read back through Cloud Control `GetResource`).
  It is built against the `CfnView` L1 from `@aws-cdk/aws-service-spec` (added to `aws-cdk-lib` in
  [aws/aws-cdk#38969](https://github.com/aws/aws-cdk/pull/38969)). Both integration tests were deployed to a test
  account in us-east-1 and their snapshots recorded.

See Appendix A for the full API and Appendix B for the CloudFormation mapping.

### Is this a breaking change?

No. This is a new construct; it does not change any existing API.

### What alternative solutions did you consider?

1. **Use `CfnView` only.** Works today with no new API, but gives no synthesis-time checks, no import by ARN and no
   `IView` type.
2. **Mixins or Facades only, no L2.** Every configurable property is a
   pass-through, so there is no hand-written mixin to offer, and the only Facade candidate (`ViewGrants`) is deferred.
   Building blocks alone would give `CfnView` and the generated `CfnViewPropsMixin`. The `IView` type, `fromViewArn`
   and synthesis-time validation are only available from an L2.
3. **A typed SQL builder for `definition`** (like `logs.QueryString`). Rejected: CDK would have to follow the service's
   SQL dialect as it evolves, and queries the builder cannot express would be impossible to write.
4. **A wrapper class for `definition`** (like `stepfunctions.DefinitionBody.fromString()`). Rejected for v1. It would
   allow adding other input forms later without a breaking change, but today it would only wrap a string.
   `definition: string` matches `PromQLAlarm.query` and `LogQueryWidget.queryString` in the same module. jsii does not
   support a `string | ViewDefinition` union, so switching later means adding a new prop and deprecating this one.
5. **Fewer synthesis-time checks** (none, or the name only). No checks would make the L2 behave like `CfnView` for
   names. Checking only the name would leave empty definitions to CloudFormation. The three checks are kept because they
   mirror the resource schema and can be relaxed later without a breaking change. The schema also caps `Tags` at 50
   entries; this is not checked, because `Tags.of()` adds tags after construction and the final count is only known
   when the L1 is synthesized.
6. **Expose `Type`, `CreatedAt` and `UpdatedAt` as attributes.** Not in v1, although the guidelines ask for every
   CloudFormation attribute:
   * `Type` is always `USER` for views created through CloudFormation, and the timestamps have no use in CDK code.
   * The awslint rule that enforced this (`resource-attribute`) is commented out, and `AlarmMuteRule` in the same
     module exposes only `Arn` of its four attributes.
   * The values stay reachable through the L1: `(view.node.defaultChild as cloudwatch.CfnView).attrCreatedAt`.
   * Adding getters to `View` later is not a breaking change. We will add them in v1 if the API Bar Raiser prefers.
7. **`fromViewName` and `fromViewAttributes`.** `fromViewName` cannot produce `viewArn` (see "Importing an existing
   view"). `fromViewAttributes` would duplicate `fromViewArn`, since the name is part of the ARN.
8. **Not throwing in `fromViewArn`** (like `Alarm.fromAlarmArn` and `AlarmMuteRule.fromAlarmMuteRuleArn`, which return
   `undefined` for the name when the ARN has no resource name). The name of a view is usually
   interpolated into another query, so an `undefined` name would synthesize as `FROM "undefined"` and fail only when the
   query runs. `fromViewArn` throws instead, like `kms.Key.fromKeyArn`. Malformed ARNs such as `not-an-arn` are rejected
   by `Arn.split` in both approaches. The agent-facing `AGENTS_CONSTRUCT_DESIGN.md` says `from*` methods must not
   validate identifiers, while `DESIGN_GUIDELINES.md` allows parsing after a token check. Removing the check later is not
   a breaking change, so we will follow the API Bar Raiser's preference.
9. **A `ViewGrants` facade.** Deferred to keep v1 minimal (see "Why should we not do this?"). A future
   `ViewGrants.read` would grant `cloudwatch:GetView` on `viewArn`; it can be generated from `grants.json` and added
   later without breaking changes, preferably after the Service Authorization Reference documents the full `view` ARN.
   Query permissions are not part of it:
   the Service Authorization Reference lists `cloudwatch:GetRecords`, `cloudwatch:GetMetricData` and
   `cloudwatch:ListMetrics` for `StartTelemetryQuery`, and none of them accepts a `view` resource type, so querying
   cannot be scoped to one view.
10. **An alpha module.** Not chosen: the construct ships in the stable `aws-cloudwatch` module, like `AlarmMuteRule` and
    `PromQLAlarm`, because the surface is one resource with four pass-through props. We will move it to an alpha module
    if the CDK team prefers.
11. **Requiring `viewName`.** Rejected. `definition` is the only property the resource requires, and when `Name` is
    omitted CloudFormation generates a valid one (`view.` followed by the lowercased stack name, logical ID and a random
    suffix), so the minimal example needs no name. This follows the CDK practice of preferring generated names.
12. **Other names for `definition`**, such as `query` or `sql`. Rejected: `definition` is the name used by the
    `CreateView` API and by the CloudFormation resource.
13. **Validating `SELECT *` in `definition`.** Rejected: `SELECT *` inside a definition works; the restriction applies
    to queries that read from a view, which the construct does not create. The README warns about it instead.
14. **A static `View.isView(x)` type check.** Not in v1. `AGENTS_CONSTRUCT_DESIGN.md` asks for an `isFoo` method on
    every construct class, while `DESIGN_GUIDELINES.md` asks for one only when code needs to compare types. Nothing in
    v1 branches on the concrete `View` type, and no hand-written class in `aws-cloudwatch` defines such a method.
    Adding it later is not a breaking change, so we will add it in v1 if the API Bar Raiser prefers.

### How are features decomposed into building blocks?

| Feature | Building block | Reasoning |
| --- | --- | --- |
| Definition and description | L2 props (pass-through; no hand-written mixin) | About the view itself, but values pass straight through; `definition` is required, which a mixin cannot model |
| View name | L2 prop with synth-time validation | Identifier handled by `physicalName`; validation is ordinary prop validation |
| Tags | L2 `tags` prop | Wired to the L1; `Tags.of()` reaches `CfnView` |
| Import by ARN | L2 `fromViewArn` | Referencing unowned resources is an L2 responsibility |
| Read access (`GetView`) | Facade `ViewGrants` — deferred | Serves the grantee, not the view |
| Query permission | Not a view building block | Required IAM actions have no `view` resource type |
| Metrics, events, resource policy, encryption | Not applicable | None exist for views |

Properties not modeled by the L2 are available through the generated `CfnViewPropsMixin` from
`@aws-cdk/cfn-property-mixins`.

### What are the drawbacks of this solution?

* The construct adds little beyond `CfnView`.
* The name check duplicates the resource schema pattern; it must be updated if the service changes the pattern.
* `fromViewArn` carries its own ARN parsing because the generated L1 helpers follow the Service Authorization Reference,
  which currently omits the id (see "technical solution").

### Are there any open issues that need to be addressed later?

* `ViewGrants.read` (`cloudwatch:GetView` on `viewArn`), deferred to keep v1 minimal (see alternative 9). Preferably
  added after the Service Authorization Reference documents the full `view` ARN: the service team confirmed that the ARN
  is `view/${ViewName}/${ViewId}`, and a correction to the reference (which documents `view/${ViewName}`) has been
  submitted. `cloudwatch:ListTagsForResource`, `cloudwatch:TagResource` and `cloudwatch:UntagResource` still do not list
  `view` as a resource type in the reference; this has been reported to the service team.
* Whether `fromViewArn` should throw on an ARN without a resource name or return an `undefined` name (see
  alternative 8). Decided by the API Bar Raiser during review; relaxing the check later is not a breaking change, but
  adding it later would be.
* `viewType`, `viewCreatedAt` and `viewUpdatedAt` attributes, if users ask for them.

## Appendix

### A. Proposed API

```ts
export interface IView extends cdk.IResource, IViewRef {
  /** @attribute */
  readonly viewArn: string;
  /** @attribute */
  readonly viewName: string;
}

export interface ViewProps {
  readonly definition: string;                  // 1-10000 characters
  readonly viewName?: string;                   // @default - generated by CloudFormation
  readonly description?: string;                // @default - no description
  readonly tags?: { [key: string]: string };    // @default - no tags
}

/**
 * @resource AWS::CloudWatch::View
 * @stateless
 */
export class View extends cdk.Resource implements IView {
  public static fromViewArn(scope: Construct, id: string, viewArn: string): IView;
  public get viewArn(): string;
  public get viewName(): string;
  public get viewRef(): ViewReference;
  constructor(scope: Construct, id: string, props: ViewProps);
}
```

### B. CloudFormation mapping

```ts
new cloudwatch.View(this, 'AppErrors', {
  viewName: 'view.app_errors',
  definition: "SELECT `@timestamp`, `@message` FROM \"logs.default\" WHERE `@logGroupName` = '/my/app'",
  description: 'Error lines from /my/app',
  tags: { team: 'payments' },
});
```

Synthesizes to:

```yaml
Type: AWS::CloudWatch::View
Properties:
  Name: view.app_errors
  Definition: "SELECT `@timestamp`, `@message` FROM \"logs.default\" WHERE `@logGroupName` = '/my/app'"
  Description: Error lines from /my/app
  Tags:
    - Key: team
      Value: payments
```
